## Method (rule question still open)

The shot is a **vector rotoscope of the source**. Each key is built from measurements of one source frame, in paint
values (the film's grade inverted by `trace/grade.py`):
- a 14-level value study (simplified region outlines);
- solid blacks and white-ink highlights as outlines;
- the ink lines (traced centre lines with a width per point), redrawn as tapered strokes.

No pixels are stored, but this is a dense automatic trace of the source frames. Other shots use the same method and
flag the same caveat. **No ruling has been given on whether this is allowed.** If it is not, the shot has to be
redrawn. The per-key value corrections (`s04/tcorr.js`, measured against each source frame on a 24 px grid) are also
still in place, and the question over them is open too. Pass fix2 removed one of the measured-texture inputs: the
hatching no longer uses each key's measured weight field (`K.dw`). Its regions are now drawn by hand, and only the
hold key's stroke direction (`K2056.dv`) is used.

**Motion.** Each key reaches its neighbouring frames through a measured DIS optical-flow field (24 px grid), drawn as
a mesh by `s04/morph.js`. Keys fall on every 3rd frame through the glide and one key covers the hold. After that
they fall on every 4th frame into the swing, then every frame from 21.32. The landing (19.56–20.24) draws the hold
key, carried by its flow, and uses the per-frame keys only inside the owl's measured outlines.
